# Adjacent literature: skills, plugins, memory, and coding-agent adaptation

*A primary-source review connecting direct Skill benchmarks with procedural memory, retrieval, adaptation, and coding-agent research.*

*Research note prepared 2026-08-31. This is an adjacent-literature review, not the central review of the named personalized-skills paper.*

## Scope and reading standard

Here, “skill” is used as an operational umbrella for a reusable instruction, procedure, executable program, tool composition, or experience-derived memory that is supplied to an agent at inference time or accumulated across tasks. “Plugin” is used more narrowly for an extension that exposes tools/APIs or an agent interface. These are related but not interchangeable: a tool call can be correct without being a reusable skill, and a skill can be useful without changing model weights.

I prioritized primary papers and their arXiv/conference pages. The 2025–2026 skill and memory papers below are preprints unless a venue is explicitly stated; their numerical claims should be treated as provisional until independently reproduced. “Capability evidence” means that a system can perform the proposed operation under the paper’s setup. It is not evidence of durable developer productivity, safety, or general user benefit.

## Top synthesis

1. **Reusable procedures can compound performance, but retrieval and fit are the gating variables.** SkillsBench v4 provides the cleanest paired evidence: curated skills raise pass rate across its matched conditions, while the realistic-skills study finds that gains shrink toward no-skill baselines when the agent must search a large library and select imperfect matches. Voyager, ExpeL, Reflexion, SkillCraft, and the newer procedural-memory studies show the mechanism in bounded settings. A library should therefore be evaluated as a *retrieval-and-execution system*, not as a bag of prompt text.
2. **Abstraction beats raw history, but abstraction can over-specialize.** The procedural-memory benchmark reports that LLM-generated procedural abstractions transfer across changed entities better than embedding retrieval of trajectories. The continual-learning study finds that abstract procedures transfer more reliably than detailed trajectories, while negative transfer disproportionately hurts hard tasks. AFTER likewise reports broad and role-specific skills; cross-role generalization is not automatic.
3. **Tool/API research establishes a plugin capability, not personalization.** Toolformer, Gorilla, and ToolLLM show that models can learn when/how to call APIs, retrieve API documentation, and compose multiple calls. Their datasets are mostly curated or machine-generated and evaluate API correctness on fixed catalogs. They do not establish that a plugin learns a particular developer’s conventions, remains reliable as tools change, or improves end-to-end engineering outcomes.
4. **Coding evidence points to context/interface design as a major causal lever.** RepoCoder shows iterative repository retrieval improves completion; SWE-agent shows an agent-computer interface can materially change issue-resolution results. Both are useful analogies for project-specific skills, but neither is a longitudinal study of developer interaction histories. Repository benchmarks also conflate model, prompt, retrieval, interface, and execution effects.
5. **Cost, stale knowledge, and harmful transfer belong in the primary metric set.** SkillCraft reports large token savings in its skill-reuse protocol, while the realistic-skills work reports that skill benefits are fragile. Memory papers identify retrieval competition/forgetting; the practical implication is to log success, cost, latency, stale-skill rate, and negative-transfer rate—not just pass rate.

## Source notes and implications for an agent-Skills program

### 1. Direct skill-library and procedural-memory evidence

**Li et al. (2026), SkillsBench v4.** The latest arXiv record is v4, revised 2026-06-14 (not the older v1/v2 numbers). Its paired design compares the same 87 tasks with and without curated skills under 18 model-harness configurations, reporting 33.9% → 50.5% average pass rate (+16.6 points), with +4.1–25.7-point configuration-level gains. The result is unusually useful because the no-skill condition is matched and verifiers are deterministic; the paper also reports that focused bundles of at most three modules beat larger/exhaustive bundles. This supports a focused-skill and matched-ablation design. It does not answer whether an agent can discover the right skill from a large library or whether developer-specific skills help: skills are curated and paired to tasks.

**Liu et al. (2026), How Well Do Agentic Skills Work in the Wild.** This is the most directly relevant stress test for a skills product: the agent must find a useful artifact in a 34k-skill collection rather than receive a hand-selected skill. The paper’s central empirical claim is conditional: skills help when relevance and quality are adequate, but the benefit erodes under realistic retrieval and selection. Query-specific refinement is presented as a recovery mechanism, including the reported Terminal-Bench 2.0 improvement. For a product, this supports measuring retrieval recall, selection precision, refinement success, and no-skill deltas separately. The preprint does not establish that the same selection dynamics hold for developer-authored skills or personalized coding traces.

**Chen et al. (2026), SkillCraft.** SkillCraft operationalizes a skill as a higher-level composition of atomic tools that can be saved and reused. Its contribution is primarily a benchmark/protocol: repeated structure and cross-task reuse become measurable. The reported 80% token reduction is evidence of efficiency under its “Skill Mode,” not a general claim that every skill library reduces cost. The most useful design lesson is to evaluate cold-start skill acquisition and warm-start reuse independently, with success and token/wall-clock cost reported together.

**Belikova et al. (2026), AFTER.** AFTER is notable because it explicitly tests local improvement and transfer across tasks, roles, and model backbones. The reported 3.7–6.7-point refinement gains and 73.1% cross-model accuracy from diverse traces suggest that provenance diversity may improve portability. At the same time, the paper reports some skills becoming role-specialized. A real system should retain scope metadata and reject cross-role reuse by default when evidence is weak.

**Hu, Long & Wang (2026).** This study reframes continual learning as a memory-management problem. Its key warning for Skills is that adding a persistent artifact does not eliminate forgetting: retrieval competition, representation, and organization decide what is actually available at inference. “More granular” indexing is not unconditionally better. This supports bounded, auditable libraries with explicit replacement, staleness, and rollback policies.

**Kohar & Krishnan (2025).** By isolating retrieval from execution, this benchmark helps prevent a common evaluation mistake: treating a successful downstream run as proof that retrieval understood a procedure. Its generalization cliff implies that lexical/vector similarity may be inadequate when a developer renames files, changes frameworks, or expresses the same intent in unfamiliar language. Procedural summaries should encode preconditions, ordered steps, expected observations, and failure recovery—not only keywords.

**Liu et al. (2026), HASP.** HASP turns a passive instruction into a program with activation and intervention hooks. This is relevant to plugins that need to enforce a sequence, check a state, or correct a repeated failure. However, its claims mix inference-time intervention, post-training, and controlled evolution; those should be treated as different interventions in any replication. It is evidence for an executable skill architecture, not evidence that automatic skill evolution is safe.

### 2. Memory and tool-use foundations

**Voyager, ExpeL, and Reflexion** form a useful progression: executable code skills in an embodied environment; natural-language insights extracted from trajectories; and verbal reflections retained as episodic memory. Together they support the mechanism “observe outcome → summarize reusable procedure/lesson → retrieve it on a later attempt.” They also expose portability limits: Minecraft behaviors, ALFWorld lessons, and HumanEval reflections are not automatically project-specific coding skills. In particular, benchmark feedback (compiler/tests/environment rewards) is much cleaner than the sparse, ambiguous feedback in developer interaction histories.

**Toolformer, Gorilla, and ToolLLM** establish complementary plugin capabilities: learn an invocation policy, ground calls in changing documentation, and retrieve/compose among thousands of APIs. Their strongest evidence is about syntactic/API-use competence on fixed or constructed catalogs. A production plugin layer still needs authorization boundaries, version and schema checks, outcome validation, latency/cost accounting, and defenses against malicious tool descriptions. None of these papers should be read as evidence that a model has learned a developer’s preferences.

### 3. Coding-agent analogues

**RepoCoder** demonstrates that repository context is useful when retrieval is iterative: the model’s first completion can improve the next retrieval query. This is a plausible implementation pattern for project skills, but the paper’s task is code completion rather than issue resolution or developer collaboration.

**SWE-agent** demonstrates that the interface through which an agent reads, edits, and tests code changes outcomes. For Skills, this suggests evaluating not only the text of a skill but also the available commands, observation format, test feedback, and action budget. Its benchmark score is capability evidence under a specified ACI, not a causal estimate of productivity or maintainability.

## Practical evaluation hypotheses suggested by the literature

- **Retrieval:** Compare no-skill, oracle-skill, library-retrieval, and retrieval-plus-refinement conditions. Report retrieval precision/recall and the fraction of runs harmed by a retrieved skill.
- **Transfer:** Hold out projects, frameworks, role vocabulary, and model backbones. Test both renamed-equivalent tasks and genuinely novel tasks; measure cross-task, cross-role, and cross-model transfer separately.
- **Quality and safety:** Track pass rate, regressions, token use, wall time, tool-call count, stale-artifact rate, and negative-transfer rate. Require provenance, scope, preconditions, and rollback for executable skills.
- **Personalization:** Use longitudinal, consented developer histories with a time split and project split. Evaluate whether the artifact improves *the same developer’s* task outcomes after controlling for model/prompt/interface changes, and include acceptance, edit distance, rework, and subjective burden—not only benchmark pass rate.
