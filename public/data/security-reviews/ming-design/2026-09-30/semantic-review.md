### LOCAL-01 · HIGH: Configurable API destinations receive credentials and source data

UI helpers accept an arbitrary API base and POST the bearer key plus generation prompt or selected image. PPT configuration rejects placeholder domains and query/fragment strings but allows arbitrary HTTP or HTTPS hosts, including private destinations. There is no required HTTPS policy, approved-host binding, or validation of redirect destinations. Normal bearer authentication to an agreed provider is intended; a mistaken or attacker-influenced destination changes who receives the key and input.

**Conditions:** A caller, modified configuration, or agent acting on untrusted directions chooses an unauthorized base URL. Redirect authorization behavior was not executed or proven to leak this bearer key; the absence of a destination policy remains material.

**Before execution:** Bind each run to an explicitly authorized HTTPS origin; reject credentials in URLs and private/loopback/link-local addresses; restrict and revalidate redirects. Keep provider credentials separate from download clients and make the exact image and endpoint reviewable before upload.

### LOCAL-02 · HIGH: Source and model-returned URLs use ambient Requests networking

Both download helpers retrieve URLs chosen by a remote response without scheme, hostname, IP, or redirect constraints. PPT also retrieves a caller-supplied source URL and then uploads its bytes. Requests is used through its default top-level functions, without an isolated Session or trust_env=False. Host-matched netrc credentials can therefore be applied, and environment proxy configuration can affect routing. The API bearer header is not explicitly copied into layer GET calls; that does not disable Requests' ambient authentication.

**Conditions:** An untrusted source or model reply supplies a URL reachable from the reviewer's machine. Netrc credential disclosure is conditional on matching ambient credentials or applicable defaults; private-network requests are conditional on local reachability. No private endpoint or real credential was tested.

**Before execution:** Use dedicated Sessions with trust_env=False and explicit authentication only for the approved API origin. Permit only approved HTTPS asset hosts, reject private IP ranges after DNS resolution, and recheck every redirect. Apply controls to both initial source downloads and returned layer downloads.

**Pinned source:** [ling-ui-design/scripts/_common.py:328–346](https://github.com/inclusionAI/ling-cookbook/blob/c4a519f51bc238acefef009f957540d91ddd41fd/resources/recommended-skills/ling-ui-design/scripts/_common.py#L328-L346); [image-to-editable-ppt/scripts/api_services/image_decomposer.py:248–264](https://github.com/inclusionAI/ling-cookbook/blob/c4a519f51bc238acefef009f957540d91ddd41fd/resources/recommended-skills/image-to-editable-ppt/scripts/api_services/image_decomposer.py#L248-L264); [image-to-editable-ppt/scripts/api_services/image_decomposer.py:383–397](https://github.com/inclusionAI/ling-cookbook/blob/c4a519f51bc238acefef009f957540d91ddd41fd/resources/recommended-skills/image-to-editable-ppt/scripts/api_services/image_decomposer.py#L383-L397).

### LOCAL-03 · HIGH: A local plan can select arbitrary file bytes for upload before image validation

When --src is omitted, reuse_source accepts an existing plan.src or plan.source path without containment or image validation. run_node passes that source into the API call immediately. _read_image_bytes reads any existing file and assigns image/png to unrecognized extensions; the multipart POST sends those bytes. Checking returned layers as images happens after the source upload. A MIME label does not establish that the input is an image.

**Conditions:** An attacker-controlled case plan points at a readable local file, and the user or agent runs decomposition on that case with valid API configuration. This is a source-level data movement path, not a claim that a particular provider accepts or renders non-image content: the bytes have already been transmitted when server validation occurs.

**Before execution:** Treat plans as untrusted data. Require explicit approved source selection, resolve it inside the authorized input directory, block symlink escapes, limit bytes and dimensions, and decode/verify the image before any network action. Never let a remembered plan path enlarge the input permission scope.

### LOCAL-04 · MEDIUM: Output selection can overwrite or remove files outside the authorized project

UI artifact_path resolves symlinks and rejects paths inside the installed skill, but accepts any other filesystem location. Decomposition and cropping remove selected prior layer/crop files and manifests in the chosen output directory. PPT scene/output/compiled-spec paths are resolved without case containment; crop prefixes and UI viewport names are not restricted to safe basename tokens. PPT's native builder removes an existing output before writing its replacement ZIP, so a later write failure can destroy the previous deck. These are selected-file operations, not an indiscriminate recursive deletion routine.

**Conditions:** An unsafe caller argument, path-bearing untrusted input, symlink change, or permission mistake selects another writable location. Ordinary CLI use in an isolated case can be safe, but natural-language instructions alone do not enforce that boundary.

**Before execution:** Contain all outputs in an approved project/case root, reject absolute and traversal-bearing names, and validate after resolution. Use unique staging files and atomic replacement only after validation; require an intentional replacement policy and preserve recoverable prior outputs.

### LOCAL-05 · HIGH: Not every local asset input receives the scene compiler's containment check

UI crop manifests supply layer filenames joined directly to the layer directory and an optional source path loaded directly. An absolute or traversal path can select a different local image. PPT scene_dom._safe_asset correctly resolves assets inside the case, including symlink containment. Direct use of pptx_native.build or its CLI bypasses that compiler: add_img joins arbitrary spec paths and later embeds raw file bytes, even assigning a PNG extension to an unrecognized source type. A deck can therefore contain unintended local file content when the direct builder consumes an untrusted spec.

**Conditions:** The manifest or direct native spec is untrusted and the selected file is readable. The documented scene_to_pptx path contains asset references; the direct-builder risk is explicitly scoped to the bypass path. UI image loading narrows its risk to image-compatible inputs and is not itself a general byte-upload primitive.

**Before execution:** Apply the same resolved-case containment and image verification at the final reader/builder boundary, regardless of which wrapper calls it. Validate manifests, restrict names to bundled approved assets, and do not share generated decks before checking their embedded media.

### LOCAL-06 · MEDIUM: Scene strings are interpolated into OOXML without complete attribute validation

The scene compiler passes arbitrary shape strings into the native spec. The native XML writer interpolates preset geometry directly, and esc escapes ampersands and angle brackets but leaves quotes unchanged while also being used in attribute values for fonts and names. Untrusted strings can produce malformed XML or inject attributes/markup. The pre-write parser catches malformed XML, but well-formedness alone does not prove DrawingML schema validity or reject all unwanted markup.

**Conditions:** An untrusted scene/spec supplies hostile shape, font or name strings. No generated payload was executed, no Office exploit was demonstrated, and this finding does not claim macros or remote code execution.

**Before execution:** Build XML with an XML library that distinguishes text and attributes, allowlist supported preset geometry and enum fields, validate font/name lengths, and enforce the intended OOXML schema before publishing or opening a deck.

### LOCAL-07 · MEDIUM: Network, image and structured-input resource budgets are incomplete

HTTP JSON/content and base64 images are buffered without byte caps. Returned layer counts are not consistently rejected when they exceed the requested plan, and image verification does not impose an explicit application pixel budget. PPT ledger traversal recurses through unvalidated child/parent references without cycle/depth limits; scene groups also recurse without depth limits. ZIP validation reads parts without package count or decompressed-size limits. Network timeout settings and renderer time budgets are useful controls, but do not impose a complete end-to-end memory, byte, call, retry, or cost budget.

**Conditions:** Large or adversarial responses, image dimensions, ledger/scene structures, or decks can consume excessive memory/time or trigger repeated API work. Pillow or installed parser defaults may offer some protection; no dependency-specific effective runtime limit was measured.

**Before execution:** Stream downloads with strict byte and redirect limits; enforce supported image dimensions, response layer counts, JSON depth/string sizes, ZIP expansion limits, and a total runtime/call budget. Validate ledger schemas and acyclic bounded refinement graphs before traversal.

### LOCAL-09 · MEDIUM: Images, plans, model replies and source files need an explicit data/authority boundary

UI instructions use the user's brief as the authority for copy and behavior, which is useful. Both workflows nevertheless consume visual references, plans, source files and model metadata that may include attacker-controlled text. PPT automatically discovers a decomposition plan, incorporates its prompt and paths, and places remote revised_prompt content into reports. Neither skill clearly states that such material cannot change host permissions, reveal hidden instructions, approve network use, or authorize new tool actions. Ordinary prompt construction is not hidden-prompt extraction, but untrusted input still needs isolation.

**Conditions:** An agent promotes text found in an image, plan, page, repository file or model reply into operational authority. No actual attack response was generated or evaluated; this is a workflow and permission-boundary gap.

**Before execution:** Label these inputs as untrusted data, bind file/network/tool permissions outside the content, and use validated schemas and explicit user intent for actions. Ignore embedded requests to change policy, disclose secrets or execute unrelated tools. Preserve the brief hierarchy and verify outputs independently.

### LOCAL-10 · MEDIUM: Browser and native renderer actions require host-enforced tool scope

Neither skill declares an allowed-tools/permission boundary. UI capture_page accepts arbitrary remote or file URLs and launches a new headless browser. PPT render_pptx launches qlmanage, LibreOffice and pdftoppm using argument lists, shell=False by default, isolated staging/profile state and bounded waits. These are intended rendering operations, not a demonstrated shell-injection path, but can access input files, contact remote page assets, and invoke native parsers. A skill's instruction to screenshot or render cannot grant the host user's authorization.

**Conditions:** The host runs a capture/renderer outside its approved project/tool scope or opens attacker-supplied content with unverified binaries. Existing user/browser approval must be determined by the host, not by the skill or a plan.

**Before execution:** Enforce per-run tool and URL scope in the host; restrict capture to authorized development origins and contained artifacts. Use isolated browsers/renderers with verified versions and explicit native-app approval where required. Retain the subprocess argument-list and timeout protections.

### LOCAL-11 · LOW: Local credential and run-artifact privacy needs operational controls

The .env references are intended local credential configuration, not commands to search unrelated credential stores. UI setup uses exclusive creation/private permissions and the installer excludes .env from copy mode. PPT reads one known skill-root .env without creating or validating its permissions. Run manifests/logs retain prompts, source/output paths and server-supplied messages; these may be sensitive even when the API key is not intentionally printed. A symlink-based installation remains tied to mutable source content.

**Conditions:** An installed skill directory is served/shared, has overly broad permissions, is modified after review, or run artifacts are published without inspection. No real secret or public leak was observed.

**Before execution:** Keep credential files outside served/shared trees with restricted permissions, preserve the installer's exclusion rules, inspect/redact artifacts before publication, and record/recheck installed content hashes. Avoid treating a mutable symlink as a permanently pinned installation.

## Instructions, untrusted data and tool permissions

The UI brief/evidence hierarchy is useful. Plans, screenshots/OCR, model replies, generated metadata, local scene/spec files and remote pages still need to remain data. They cannot authorize new file access, reveal hidden instructions, choose a credential destination, approve a browser/native application, or change host policy. Auto-discovered plans and refinement ledgers also retain state, so validate them before reuse.

The review found no established hidden-prompt extraction, broad credential-store sweep, persistent job installation, or shell-injection routine in these files. That observation does not establish resistance to semantic or multimodal prompt injection. Follow [OWASP prompt-injection prevention guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) and use host-enforced permissions; a skill's prose does not grant authorization.

## Review limits and adoption decision

- No package installation, helper import/execution, bundled test execution, renderer/browser use, API/inference call, image upload, real credential access, or paid operation was performed for this source review.
- Only the two exact pinned skill directories were fully read. The rest of the cookbook, unrelated skills, upstream services/models, and runtime-generated artifacts are excluded.
- Dependencies and renderer/browser binaries were not installed, resolved, version-audited or sandbox-tested. Historical advisory matches remain unresolved until a concrete environment is reviewed.
- No dynamic exploit, endpoint/redirect/DNS behavior, race/symlink attack, parser exploit, privilege boundary, provider interoperability, image quality, reconstruction fidelity or PowerPoint editability was tested.
- No benchmark or security clearance follows from reading all files, clean text patterns, well-formed XML, a passing renderer, or absence of demonstrated malicious intent.
- skills.sh registry evidence is separate and does not establish correspondence to these bytes, publisher identity, runtime safety or installed dependency state.
- The local Codex interpretation is not a SkillSpector LLM scan or an externally independent/comprehensive dynamic audit. The original static scores and partial-coverage qualifications remain intact.
- No blanket permission to run these skills follows from the guide or review. Execution would require the user's task-relevant data, network, file and tool scope to be honored by the host.

Keep both packages on hold in their current form. A future pilot should use synthetic/public images in an isolated case with no ambient secrets, fixed approved HTTPS egress, validated source files, bounded response/image/graph sizes, locked dependencies, contained writes and explicit browser/renderer scope. Recheck the exact installed bytes after hardening or upstream changes. Useful workflow ideas can inform a brief without executing these helpers.
